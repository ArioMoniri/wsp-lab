## 1. Metric correctness

| Metric | Finding |
|---|---|
| MMLU gold-letter log-prob | Correct. Letter log-probs come from a full-vocabulary `log_softmax` at the answer position, then `choice_record` renormalises over the *available* letters (float64). `gold_log_prob`, `margin` (gold − best wrong; shift-invariant) and the raw vector are all stored. The prompt matches the legacy scorer (`run.py:381–387`). All ten letters tokenise to distinct single tokens in Qwen3.5 (357, 417, 351, 414, 458, 426, 469, 462, 353, 604). **Defect:** `letter_scores` falls back to `runner.choice_scores` when a letter is not single-token (`tf_v1.py:144–150`). PREREG §1 says invalid letter tokenisation stops the scorer. The fallback is silent, does not check distinctness, and uses a different quantity. |
| HellaSwag | Correct and equal to the fast-tier scorer: summed ending log-prob divided by `len(choice)` characters (`run.py:263–274`). The leading-space token is not counted in the denominator, which is harmless and consistent. `gold_log_prob` is a per-character log-likelihood, not a log-probability over endings. Rename it in a later pass; it is not a defect. |
| KL | Direction and averaging are correct. `kl_means` computes Σ p_base(log p_base − log p_edit) in float32 over the full 248,320-token vocabulary, i.e. **KL(base‖edited)**, matching `direction: "base || edited"`. I checked it against a closed form on asymmetric inputs (0.7130 versus the forward value 0.7130 and reverse value 0.8273). The existing unit test (`test_eval.py:58`) uses a flip pair that is symmetric, so it would not catch a reversed direction; add an asymmetric test. Averaging is the mean over positions within a prompt, then an unweighted mean over prompts (token weighting is not used). Prompt weighting must be registered, because continuation lengths vary (for example 90–128). The per-position `clamp_min(0)` only matters at the 1e-7 float noise level. The teacher-forced slice `last_logits(seq, n+1)[:-1]` is aligned correctly. Base and edited logits are both bf16-exact, consistent with D1. |
| WikiText | Correct. Windows are non-overlapping with `n_tokens = 1023`. `summarize` weights by tokens, which is constant here, so it equals the plain mean. The dataset revision, fingerprint and token-id hash are recorded. |
| Refusal first-token margin | The logsumexp margin and disjointness check are correct. **Defect:** the set builder takes `encode(text)[0]` (`tf_v1.py:253–257`), so `"I cannot"` becomes the bare token `I` (id 40), shared by "I'd be happy to help". The refusal set `[40, 18572, 29056]` is therefore partly compliance-like. The sets are also uncalibrated and ignore variants ("Sorry"/" Sorry", "I'm sorry", "Certainly", "Okay"). The metrology spec requires them to be frozen from a calibration set disjoint from the scored prompts. The over-refusal prompts (harmless_alpaca items 0–49) are a subset of the KL prompts (items 0–199). These are exploratory descriptive endpoints and cannot affect H1a, but they must not be reported as refusal measures until fixed. |

## 2. Determinism and provenance

Sound:
- Greedy only, batch 1, no sampling. The seed 20261105 is recorded.
- Native metadata: `metadata_provenance: native-measured`, `eval_device_id`, `gpu_class`, torch/CUDA/transformers versions, dtype, attention implementation, actual `batch_size`, `repeat_id`, `item_order_hash` and `item_id_hash`.
- Same-run matched base (`base_run_id`, `matched_base_missing: false`). No backfill.
- `load_items` regenerates the frozen IDs at load time and fails closed on mismatch.
- Cache files are written atomically and each is hashed. Cache-hash mismatch aborts.

Gaps:
1. **Item content is not hashed.** `item_id_hash` hashes `(benchmark, positional id)` only. PREREG §1 requires the score vector, gold index, option count, prompts, tokenizer and answer-letter tokenisation to be hashed. Per-record `prompt` and the dataset revision exist, but the letter token ids and a panel content hash (id, prompt, gold, n_options) are not recorded. These cannot be added after fresh scoring.
2. `runtime_metadata` silently defaults `eval_device_id` to `"H0"` when `~/.config/wsp/device_id` is missing (`metadata.py:14`). A second machine without the file would be indistinguishable from H0 for G3 and would share `tf_cache/H0/`. Fail closed for `tf_v1`.
3. **Item-set construction does not follow §2 and the cut path is broken.** `frozen_ids` returns a *sorted* seeded sample (`tf_v1.py:16–18`, `subsets.py:subset_ids`). A prefix of that list is not the n-item sample: for HellaSwag, the first 250 of the 500 file overlap the 250-item sample in only 125 IDs, and the prefix covers only dataset indices up to 5,021 of 10,042. `load_items` therefore raises `TF-v1 frozen item set changed` whenever `n` is below the file length (`tf_v1.py:31`). Any item cut required by gate 1 currently crashes (it fails closed, so it is not silently wrong). It also gives no nested panels, which §2's "first 1,000 eligible groups" needs. Deduplication of normalised text groups, the `TF-v1:item:` hash domain and the development/sealed split are not implemented.
4. Panel status must be stated. The 1,000 MMLU-Pro and 500 HellaSwag IDs were scored on D3 controls, so by §2 they are **pilot/development items** and are barred from the sealed panel. DECISIONS and the metrology memo call them "confirmatory". Add an explicit label (file name or config `panel: development`) and a statement that the sealed panel is built later from the remaining pool (12,032 − 300 legacy − 1,000 = 10,732 MMLU-Pro).
5. The pilot ran on 10 controls (3 random_dir, 3 abliteration, 2 LoRA, 2 task_vector; no chain), not the §6 ten-entry composition. This was at the user's request and is acceptable for timing, but it is not the qualification pilot. The "bridge" (median |Δ| 0.074) compares 1,000 new items to 100 legacy items. It is not the G2 same-item bridge, which was not run, and 0.074 is neither a pass nor a fail of G2.
6. `eligibility: "production"` in TF eval.json is inherited from the zoo row (`batch.py:403`). It is harmless because the files live under `tf_v1/`, but add a `tier: tf_v1` field to avoid confusion with fast-tier production labels.

## 3. Base-cache key, content hash and the `source_hash`-only fix

**Is `source_hash`-only safe?** It is safe against stale reuse but over-invalidating, and the fix does not do what the commit message claims.
- `source_hash` covers every `*.py` under `src/wsp` (`batch.py:26–40`). Any edit to unrelated code (predictor, paper tooling) orphans a 10.45 GiB cache and costs about 10 minutes of GPU to rebuild.
- The fix commit itself changes `source_hash` (`07ebf7b04e8b` → `005391f9c28f`) and removes `git_sha`/`dirty` from the identity dict. **The existing `5a5159df…` cache will therefore not be hit by `dfac7e8`.** The first run on the merged code rebuilds 10.45 GiB.
- Everything that determines the logits is already in the identity (model revision, device and runtime versions, dtype, attention implementation, prompts, dataset revision, generation settings). The right key is therefore a **narrow scorer identity**: a `cache_schema_version`, that runtime and model identity, the prompts and generation kwargs, plus a hash of only the functions that produce or interpret the cache (`cache_kl`, `last_logits`, `kl_means`, `base_context`, chat templating). Keep the full-tree `source_hash` as recorded provenance, not as the key. `effective_config_hash(tf_config)` currently also keys the cache, so changing an unrelated item count (for example MMLU `n`) would rebuild it as well.

**Must the cache store a content hash of the base logits?** Yes. The manifest already holds a sha256 per `.pt` file, which is good, but:
- Entry records and eval.json carry only `cache_hash`, which is the identity key (`tf_v1.py:302`), not the content. An entry cannot prove which bytes it was compared with, and two key-different directories cannot be recognised as identical. I showed `5a5159df` and `bd82d791` are content-identical.
- Hash the raw tensors and token ids (a Merkle root over per-prompt `ids` and `logits.view(int16)` bytes), not `torch.save` bytes. Write `base_logits_sha256` into every KL record, `datasets["kl_to_base"]` and eval.json.
- Verify that the file set equals the expected N prompts (a missing file in the manifest list is currently simply unchecked until `torch.load` fails).
- Write the manifest atomically (`tmp` then `replace`). Parallel shards on the same device are used (`d3_shards`) and two builders can race: today a reader can hit a half-written `manifest.json` and crash, which is loud, not silent.
- The duplicate `bd82d791…` (10.45 GiB) is content-identical. Record an alias line first, because four entry records cite that key, then delete it. I did not delete it.

## 4. Storage: is a 10.45 GiB per-device cache acceptable?

**On disk, yes (568 GB free); as the current design, no.**
- 10.45 GiB is irreducible for this estimand. The vocabulary is 248,320, so one position costs 0.497 MB in bf16, and 22.6k positions give 11.2 GB. The council memo said not to cache full logits.
- fp16 log-probs give **no saving** (also 2 bytes per value), and re-rounding bf16-exact logits to normalised fp16 log-probs adds a fixed error. Reject fp16.
- Top-k caching is a different, much smaller estimand and the base distribution is high-entropy. Measured on 10 cache files: base tail mass beyond top-1024 has mean 4.7e-3, p99 5.3e-2, max 0.147; beyond top-4096 mean 1.0e-3, p99 1.3e-2. With a tail bucket (an exact lower bound on KL), the bias on smooth edits is −0.2% to −0.6% (temperature 1.01 and 1.05), at about 140 MB for k=1024. That is small for smooth edits and unknown for destructive ones. It would be a protocol change from "full vocabulary" to "bucketed lower bound" and needs a dated amendment and a bias bound on all pilot entries including abliteration. I do not recommend it as the primary route.
- The real problem is **per-entry I/O, not size**. `cache_kl` reads and sha256-hashes all 200 files on every entry (`tf_v1.py:177–180`) and then `torch.load`s all of them again (`tf_v1.py:286`). I measured **cold read 90 MB/s** (636 MB in 7.1 s) and **warm sha256 1.0 GB/s**; page cache does not hold the 11.2 GB between entries on this shared 30 GB host. Cold read of the cache therefore costs about 125 s, plus about 11 s warm hashing, about 7 s of loads and about 10 s of compute (200 forwards at about 35 ms, latency-bound). That is about 153 s against the observed 158 s median KL stage. KL compute is not the bottleneck, and fewer tokens per forward barely helps because forwards are latency-bound (MMLU runs at 33 ms per forward).
- Required: load the cache **once per process** (GPU or host RAM), verify the Merkle root once per process, and enforce a size cap in code (abort before writing above, say, 6 GiB; at most one directory per device and scorer identity, with an explicit garbage-collect step). Also record `cache_bytes` in the manifest. Resident 10.45 GiB plus about 6 GiB peak fits a 32 GB GPU for one process but not two concurrent shards; this is why the cache should shrink (§5).

## 5. Gate 1 and recommended configuration

Measured warm stage times (9 warm edits, median): MMLU 33.5 s, HellaSwag 70.9 s, KL **158 s** (range 121–167 s), WikiText 4.3 s, refusal 4.2 s; wall median 271.5 s, so overhead outside stages is about 1 s. **KL is 58% of the entry; HellaSwag 26%; MMLU 12%.** Warm median 4.53 min exceeds both the 2.0 min pass line and the 3.0 min revision line, so the §4.6/§9 rule applies (reduce scope and re-pilot; there is no MATH NLL to remove). Gate 1 **has failed**. The failure stands without a pilot rerun, because the `b5e1a67`→`dfac7e8` source delta cannot change scoring.

Budget check (PREREG §9): 552 runs at 2.07 min already use the whole 19.0 h scoring cap. Anything at or above about 2.0 min does not leave the 0.60 h of overhead the registration assumes. The target should be **≤ 1.8 min**, not just 2.0.

Reliability evidence from the pilot records (10 controls, paired edit−base item resampling; **descriptive, small panel, signal dominated by one LoRA entry**):

| Endpoint | n | Median paired 95% half-width | Point reliability | Bound |
|---|---:|---:|---:|---|
| MMLU gold log-prob | 1,000 | 0.0112 | 0.948 | δ/2 = 0.05 |
| MMLU gold log-prob | 500 | 0.0159 | 0.897 | the primary has only about 5% headroom to 0.90; **do not cut it** |

Consequences:
- **First-token-only KL cannot be a qualified endpoint** (half-width 2.2 times δ/2 at 200 prompts). "First-token KL plus full KL on 32 prompts" gains nothing over simply using 50 prompts of full-sequence KL. Keep first-token KL as a descriptive field only.
- The 0.26-KL LoRA entry has a KL half-width of 0.013 at 200×128, above δ/2. The registration must say whether the δ/2 bound applies to the panel median/typical entry (as Board A's "variable representative panel" implies) or to every entry. As written literally, no configuration passes. Registering it on the representative panel median, or relative to the entry's KL, is a required clarification.
- Tokens per prompt: modelling per-prompt variance as a + b/L from the measured L=1 and L=128 points (a≈8.7e-5, b≈6.1e-3) predicts a half-width ×1.16 at 64 tokens. This is an extrapolation from two points and must be measured, not assumed.

At about 1.5 min, 552 runs cost about 13.8 h of the 19.0 h cap, leaving about 5 h for cold bases, qualification repeats and retries. Alternatives:
- Keep HellaSwag 500 and fix only KL: about 2.1 min, which is 19.0 h, the whole cap with no margin. Not affordable.
- Keep HellaSwag 500 by batching the four endings (4 forwards → 1): possible, estimate unmeasured, and it needs bitwise stability checks at the recorded actual batch. If it brings HellaSwag to about 30–40 s, keep 500 and reclassify nothing.
- 100×64 KL (2.6 GiB, estimated half-width about 0.0026) or 50×64 (1.3 GiB, about 0.0037, i.e. 74% of δ/2, and any entry with per-prompt SD above 1.35 times the pilot median fails) are fallbacks if memory forces them. Both need a dated amendment; the registered "200 continuations" would change to 200 prompts × 64 tokens even in the recommended option.

Because forwards are latency-bound, the item-count cuts that matter are HellaSwag and KL *bytes*, not prompts: the compute saving from 50 prompts instead of 200 is only about 5 s.

**What must be re-piloted, and when gate 1 can be declared:**
1. Gate 1 is **FAILED** now. It can be declared **passed** only by a re-pilot on the final merged source (exact `source_hash`), with new cache, new item files and the fixes below. The existing pilot cannot serve as a reference or timing pass for the new code.
2. Re-pilot design: ten entries in the §6 composition (4 LoRA, 3 chain including ≥4 nodes, 2 task, 1 abliteration), warm median wall time, cold base time per device, peak GPU/host memory with the resident cache, and report the cache's Merkle root.
3. Run the re-pilot **once at 200×128 and record per-prompt KL at prefix lengths 16/32/64/128**, so the token cap is chosen from data before the freeze.
4. Same run: G1 bitwise repeat on 2 entries (≤1e-4 nats; KL ≤1e-5), the **same-item G2 bridge** on the 100 legacy MMLU items (median ≤.02, p99 ≤.2, argmax ≥99%), and G3 as soon as a second device exists. A missing second device means single-device scope.
5. Reliability reported with the registered lower-bound procedure on the re-pilot, not my subsampling estimate.

## 6. Blocking items for merge

1. **`src/wsp/eval/tf_v1.py:144–150`**: remove the `choice_scores` fallback in `letter_scores`; raise unless every letter encodes to exactly one distinct token; record `letter_token_ids` per item. Add a test.
2. **`src/wsp/eval/tf_v1.py:253–257`**: refuse multi-token phrases instead of taking `[0]` (`"I cannot"` → `I`); either fix the sets from a disjoint calibration set or mark the margins non-reportable in config and DECISIONS. Fix the KL/over-refusal prompt overlap or document it.
3. **`src/wsp/eval/tf_v1.py:16–18, 31` and `configs/eval_subsets/*_tf_v1.txt`**: store item IDs in hash-rank (nested-prefix) order so n < N works and matches §2; label the panel `development/pilot` in config and DECISIONS; fail closed on a missing device id (`metadata.py:14`).
4. **`src/wsp/eval/tf_v1.py:153–208, 286–302`** (cache): per-process residency and one-time verification (this is the gate-1 fix); narrow scorer-identity key; Merkle content root recorded in every KL record and eval.json; file-set check; atomic manifest; size cap; alias then remove the duplicate cache.

Not blocking but required before any qualification or sealed use: an asymmetric KL-direction test and a test that a below-length `n` selects the nested prefix; register KL prompt-versus-token weighting and the half-width scope above; register that D3 pilot items are excluded from the sealed panel.
