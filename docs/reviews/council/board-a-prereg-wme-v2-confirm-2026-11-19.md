## Remaining blockers before freeze

**A. Reconcile and bind every committed root-shard hash without reading sealed contents.** Locations: PREREG §II.23.3; `panels_v2d.build_c1_panel_v2e`; `scripts/wme_v2e_build_panels.py`; `audit.panels_v2e` / `bank.closure_allocation`.

The published input lineage says **1,728 original groups / 1,761 items**, while the actual c1 manifest records **`reserved_construction_items = 1723`**. The implementation retains one representative per union-policy group (`by_r.setdefault`) with cross-objective ownership. Thus the input-item count is not proof that all 1,761 items were written to construction. Coarser grouping can legitimately explain fewer representatives; this is not evidence of evaluation leakage. But the present audit reports input counts and a subset check for the 422 exposed written items, rather than a complete root-hash-to-final-group disposition.

Publish a hash-only lineage mapping/digest and counts proving that every original root item is either a written construction representative or belongs to a committed construction-only group, with zero such groups/hashes in dev, bank, sealed test or sealed generation. Reconcile 1,761 → 1,723 and amend the literal item-placement wording if the intended rule is group reservation with representative deduplication. Explicitly authorize the disclosed construction-only exposure exception, keeping evaluation exclusions absolute. Do not add duplicate rows merely to match the prose, rebuild for favorable outcomes, or open sealed text. The isolated author-response bullet saying “Their 1,728 groups” also needs to distinguish original groups from final union-policy groups.

**B. Make the registered validity/accounting contract survive failures and resumes.** Locations: `src/wsp/wm/harness.py:run_units`, `src/wsp/wm/runguard.py:UnitGuard`, `RetryPolicy`, `CanaryBook`; production orchestration promised by §II.22.6.

- `run_units` calls `guard.after_unit` only after `fn` and `store.write` succeed. A CPU failure probe produced **zero ledger rows** after a raised technical failure. Failed evaluation time therefore disappears from the combined cap. Account failed attempts and reconcile interrupted-instance/setup/idle GPU time against an authoritative ledger; a pre-unit estimate alone is not an absolute measured study cap.
- `store.done(k)` returns cached payloads before any guard or canary check. No canary eligibility record is attached to those stored results, and neither `CanaryBook` nor `RetryPolicy` is called by this path. A result scored before a failed end canary can therefore be reused as complete unless an additional, currently unshown production layer prevents it. Integrate retained/ineligible versus eligible status and first-canary-valid chronological selection into resume/result consumption.
- Retry/relaunch counts and canary events live only in memory. Constructing a new `RetryPolicy` after three attempts restarts the counter at one. Persist and reload them across process/instance relaunches; require the production guard and launch validity attestations rather than relying on an optional `guard=None` argument and docstrings. A CPU orchestration test should cover failure, failed end-canary, process restart, exhaustion/fallback and first-valid result selection together.

These are technical repairs to execute the already registered policy. They require no scientific redesign, new exploratory efficacy feedback or reviewer GPU run. Until fixed and independently checked, change 6 cannot be certified closed and the authors' “all seven closed” statement is premature.
