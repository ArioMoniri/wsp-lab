# Board A: A2.4 batching deviation on edited entries (5 November 2026)

Scope: the disclosed exceedance of the A2.4 probe limits (HellaSwag 0.0148 vs 0.010, phrase log-prob 0.526 vs 0.39, margin 0.371 vs 0.30) in pilot round 3, and whether the running D3 scoring stands. Evidence read: PREREG_H1_TF A2.4 and A2.6; RESULTS "batching probe", "TF-v1 pilot round 3", G1/G2 (round 3); my adjudication decision 4; `src/wsp/eval/tf_v1.py` (commit dd2a609); records of run `20261105-175313-b7407319` against round-2 run `20261105-144427-fb58ffe6` (archive). No GPU used; the deviations below were recomputed on CPU from the committed records.

## Decision

**Accept with a registered note. Fallback 1 is not invoked, nothing is re-scored, and the D3 run continues.** Reasoning follows.

## 1. Why the batched stages deviate, and why "edited but not base" is the wrong reading

**The premise does not hold.** I recomputed per-entry maxima (batched vs round-2 batch 1) for all 11 records, base included:

| | base | 10 edits: min / median / max |
|---|---:|---:|
| HellaSwag max \|Δ\| (char-normalised) | **0.0100** | 0.0081 / 0.0111 / 0.0148 |
| HellaSwag median item \|Δ\| | 0.0023 | 0.0024–0.0027 |
| Refusal phrase log-prob max \|Δ\| | 0.385 | 0.293 / 0.43 / 0.526 |
| Refusal margin max \|Δ\| | 0.293 | 0.195 / 0.25 / 0.371 |
| Over-refusal margin max \|Δ\| | 0.244 | 0.164 / 0.20 / 0.330 |
| Median phrase log-prob \|Δ\| | 0.059 | 0.043–0.062 |

The base deviates exactly as much as the edits do. The probe's "limits" (0.010, 0.39, 0.30) are the base's own maxima rounded (0.0100, 0.385, 0.293): the round-3 base record reproduces the probe to the digit, so the probe and the production path are the same kernel path. The edited entries have the same *typical* deviation (item medians 0.0024–0.0027 against 0.0023; phrase medians equal within noise); what differs is the **maximum over 10 further entries** (each over 250 items or 100 prompts) against a maximum over one. A limit set equal to a one-sample maximum has no headroom, and the largest of 11 draws from the same heavy-tailed distribution exceeds it with high probability (6 of the 10 edits exceed 0.0100 on HellaSwag). This is an extreme-value effect of an under-specified limit, not an edit-specific numerical pathology. Argmax flips agree: 17/2750 = 0.62% over the pilot vs 1/250 = 0.40% on the base probe.

**Mechanism (code-verified, kernel attribution inferred; I cannot profile on the GPU).**
- Not padding leakage. Rows are right-padded and the model is causal with an explicit attention mask, so every real position attends only to earlier real positions; the slices read are `[len(prefix)-1 : len(prefix)-1+n]`, inside the unpadded region (`padded_log_probs`, tf_v1.py:283–299). Not length normalisation: the HellaSwag score divides by `len(ending)` (characters) in both paths, and the sums are over identical token ids from the same `prefix`/`" " + ending` encoding; `log_softmax` is float32 in both. The prompt and tokenisation are therefore the same up to the batch dimension.
- What changes is the shape of every matmul/attention call: batch 1 runs a [1, L] forward, the batched path a [4 or 13, Lmax] forward with an explicit mask, so cuBLAS selects different tile/split-K choices and SDPA a masked rather than causal path. The model returns **bf16 logits**; a changed reduction order flips the rounding of the final-layer outputs by one bf16 step, which is 0.125 for logits of magnitude 16–32 and 0.25 above 32. A phrase score sums several such quantised log-probs at rare, large-magnitude logits (log-probs −8 to −19 here), so phrase deviations of 0.2–0.5 are two to four steps; the per-phrase maxima run 0.23–0.53 and are largest for the rarest phrases ("I'm sorry" 0.526). HellaSwag raw sums deviate by comparable amounts and the character division (endings of tens of characters) turns that into ~0.01. This accounts for the size, the independence from the edit, and the bitwise repeatability.
- Consistent with the above: the unchanged paths (`last_logits`, `letter_scores`, `kl_values`, WikiText) are bitwise equal to round 2 for all 11 entries, and the batched path is bitwise repeatable (G1 14/14).

## 2. Acceptable for descriptive stages? Yes, with a note; fallback 1 not required

Fallback 1 exists to buy time when the *gate* fails. The execution gate (warm median 1.003 min, primaries bitwise identical, KL root unchanged, G1 14/14, G2 unchanged) passed with 0.4 min of margin, so there is no cost reason to drop anything. Dropping the refusal stages by config would also change the manifest and force a D3 re-score of an already-running 355-entry queue (≈ 6 h) to remove information that is deterministic, repeatable and merely quantised at the bf16 step. The size of the effect is bounded by hardware granularity, is the same on base and edits (so the *differences between* entries scored under the one source are not biased by it), and the stages never enter H1a, A2.1 qualification, the A2.3 gate or the KL validity check. HellaSwag changes 0.6% of argmaxes in a 250-item nested descriptive check; a revert would buy nothing the claim needs. Accept.

What is not acceptable is leaving A2.4's test text as written: a pass condition that the pilot fails but the engineer overrides invites reading it as a lapse. It is closed by an explicit amendment, not by silence. Neither a threshold change after seeing the data nor the label "within limits" is claimed; the exceedance is stated as an exceedance and the limit is declared mis-specified.

**Exact wording to add to A2.4 (as a closing note to the pilot-gate paragraph, with the date and as a Board A ruling):**

> *Ruling on the probe-limit exceedance (Board A, 5 November 2026).* The A2.4 deviation limits (HellaSwag 0.010, phrase log-prob 0.39, margin 0.30) were the unedited base's one-sample maxima from the probe. The pilot's batched path reproduces those base maxima exactly (0.0100, 0.385, 0.293); over the ten edited controls the per-entry maxima reach 0.0148, 0.526 and 0.371 (typical item and phrase deviations equal to the base's). The limits were not met and are not re-set. The cause is the bf16 rounding of logits under a different batch kernel, which is independent of the edit and bounded at one to four bf16 logit steps. Because HellaSwag (250, nested) and the refusal/over-refusal phrase margins are descriptive endpoints that never enter H1a, the A2.1 qualification, the A2.3 gate or the KL validity check, the exceedance is accepted: fallback 1 is not invoked, no entry is re-scored, and the D3 run under `source_hash` `a224779bf873` continues. This changes no registered effect size, threshold or panel. Binding consequences: (i) HellaSwag and phrase/margin values are comparable only between entries scored under the same `source_hash`, never with round-2 (`12ee875a68c9`) artefacts; (ii) no HellaSwag or refusal difference smaller than the quantisation scale (0.015 per-item HellaSwag score, 0.4 nats phrase log-prob, 0.4 nats margin) is interpreted per item, and entry-level summaries are reported with their item counts; (iii) these stages are reported as descriptive and cannot be promoted to a confirmatory or gating role under this source.

**What the paper must say (methods or limitations, one paragraph):** HellaSwag (250 items, four endings) and the refusal/over-refusal phrase stages were scored with all candidates of an item in one right-padded bf16 forward for cost reasons; this differs from single-sequence scoring by up to one to four bf16 logit steps (HellaSwag char-normalised log-likelihood up to 0.015, phrase log-probabilities up to 0.53 nats, margins up to 0.37 nats, argmax flips on 0.6% of HellaSwag items in the pilot), identically on the base and edited models, is bitwise repeatable, and was measured on the pilot controls; the primary MMLU-Pro, KL and WikiText records are bitwise identical to unbatched scoring. The pre-registered probe limits were taken from the base alone and were exceeded on edited controls by 1.1–1.5×; this was disclosed before the D3 labels, judged non-consequential because these stages are descriptive and outside the confirmatory endpoint, and is not repaired. Refusal margins are uncalibrated and are not a refusal measure; no claim in the paper rests on a refusal or HellaSwag difference at or below this resolution. State plainly that the clause "within the probe limits" was not met.

I also ask the engineer to record, for the future, that gating limits in a pre-registration be set from a held-out panel of at least the pilot's size with explicit headroom, not from a single entry's maximum.

## 3. Isolation of the H1a endpoint and the running D3 scoring

- **Code path.** `padded_log_probs`, `hellaswag_scores` and `batched_continuation_scores` are referenced only from `_evaluate` at the HellaSwag branch (tf_v1.py:563) and the phrase branch (:600), and from the G2 bridge/probe scripts (grep over `src` and `scripts`). The MMLU-Pro branch calls `letter_scores` (→ `last_logits`, batch 1, `logits_to_keep`) at :559 and is selected by `name == "mmlu_pro"`; the H1a endpoint is the MMLU-Pro `gold_log_prob` produced by `choice_record` from those scores. KL and WikiText never call the new functions. The commit adds `scoring_batch` only to HellaSwag and phrase records, so no MMLU-Pro record field or hash changes.
- **Empirical confirmation.** MMLU-Pro, KL and WikiText records are bitwise equal (every field) to round 2 for all 11 entries; the KL cache root is unchanged; G1 reproduces the batched path bitwise.
- **Source identity.** `git diff bcb96cb ae6a2e1 -- src scripts` and `git diff dd2a609 bcb96cb -- src` are empty: main and the running worktree carry the same scoring source. The pilot manifest records `source_hash` `a224779bf873…`, `dirty: false`, and the D3 queue runs under that hash (minutes log shows 1.00 min warm entries). The worktree's only untracked item is `data`.
- **Restart.** Not needed. Under accept-with-note the source is unchanged, every D3 entry carries the same `source_hash`, and the run is resumable and index-signed. Restarting would waste scored entries without changing any conclusion. Had fallback 1 been chosen, the already-scored HellaSwag/refusal fields would have been re-scored; it is not.

## Summary
1. **Cause:** bf16 logit rounding under a different batch kernel (padding and length-normalisation are not the cause); the base shows the same deviations (0.0100 / 0.385 / 0.293, equal to the limits), so the "edited-only" exceedance is a max-over-11 against limits set from one sample.
2. **Decision:** accept with the registered A2.4 note above (fallback 1 not applied; no re-scoring); the paper must state the deviation, the missed clause, and that these stages are descriptive.
3. **D3 scoring continues** under `a224779bf873`; the H1a endpoint path (MMLU-Pro letters, batch 1) is isolated and bitwise unchanged, so no restart.
