## Verdict

**REVISE.** The HF path change is supported by strong evidence (458/458 identical per-item records against main's canonical run). The blocking items are documentation and hygiene: one format violation, a mislabelled "best" configuration, timing conditions that are not recorded, and omitted vLLM score deltas. None requires a code change to the production path. Nothing introduced here changes the scores of the current configuration.

## Blocking

**B1. `ruff format --check` fails.** `tests/test_eval.py:102-103`: `pad_token_id = 0` is followed directly by `def encode` with no blank line. Introduced by this branch; main is format-clean. `ruff check` passes. Fix: add the blank line.

**B2. `docs/BENCH_EVAL.md` (table row `hf-best`, line 43; Recommendation, line 48) presents a configuration that was never selected.** `data/runs/perf/hf-best.yaml` has the same `generation` block and the same `benchmarks` dict as `configs/eval_fast.yaml`. Only key order differs: `yaml.safe_dump` sorts keys, so benchmarks run alphabetically. The static and compile options were not written because neither passed the gate: static scored 0/32 agreement and compile crashed. The inline script in `scripts/perf_eval.sh` writes `hf-best.yaml` unconditionally, so "hf-best" is the production config re-timed. `scripts/perf_report.py:84` then recommends it as "the fastest measured path satisfying the agreement gate". The 6.177 vs 6.152 gap is run-to-run timing noise: the two runs did identical work (203,119 tokens, same signature, per-record identical; see N1).
- Fix: relabel as a re-timed production config, state that no optimised HF path passed the gate, and correct the `hf-best` wording in `docs/DECISIONS.md` D3 addendum 2.

**B3. Host load and concurrent jobs are not recorded.** The acceptance criterion asks for host load to be recorded; no artefact contains it. During the benchmark window (08:21–08:47 UTC), `wsp.features.extract` (tmux `p3-extract-v4`) ran four workers at about 97% CPU each, from 08:05 onward (etime 46:26 at 08:51). Load average was 7.6 on 8 vCPUs at 08:51. The D3 job started at 08:49, after the benchmark. Each path was run once.
- Noise floor: identical work at identical settings differs by 0.4% in wall time (6.177 vs 6.152). vLLM's 6.104 is 0.8% below HF, i.e. within about 2× that floor.
- Fix: record load and concurrent GPU/CPU jobs per run (or state that the host was not controlled), and state the noise floor. The D3 decision rule (vLLM must give ≥3× to change plan) is not close, so the decision stands. The defect is the missing record.

**B4. vLLM's score changes and timing definition are omitted from `docs/BENCH_EVAL.md`.**
- Full-entry scores differ from HF on the same entry (`data/runs/perf/hf-b32` vs `vllm`): gsm8k 0.14 → 0.06 (10/50 items flip), ifeval 0.44 → 0.36, math500 0.08 → 0.04, over_refusal 0.18 → 0.16 (15/50 items flip), refusal 1.00 → 0.98. None of this is reported; the doc gives only timing and the greedy probe.
- Timing definition: the doc says tokens/s is "divided by generation wall time". For vLLM the timer starts before the snapshot export and engine start (`src/wsp/eval/vllm_adapter.py:58`). `vllm.log` shows two engine inits per entry (21.7 s and 22.2 s), so the reported 713.9 tokens/s is understated.
- Fix: report the metric deltas, state that the vLLM path is not score-equivalent and is not adopted, and either exclude startup from tokens/s or say explicitly that it is included.

## Non-blocking

**N1. HF production path: equivalence verified.** Main's canonical run of the same entry (`data/zoo/qwen3.5-0.8b/4463696a4c62e8f3`, git 49c8321, eval_fast, batch 32, seed 0) matches the branch's `hf-b32` on all 458 records keyed by (benchmark, item_id), including the choice-scoring `extra` fields. Every summary metric is identical (wikitext_ppl 22.8633, KL 0.0013905, and the rest). The `run.py` delta between 49c8321 and main is the `trust_remote_code` kwarg, which is a no-op for Qwen3.5 (allow-list is LFM3 only). Caveat: one entry, one seed, one GPU. `hf-b32` vs `hf-best` is also identical per record. HF is therefore run-to-run reproducible at fixed settings.

**N2. Static cache is not score-equivalent; keep it disabled.** Probe `probe-static.json` vs `probe-hf.json`: 0/32 exact tuples at 1024 tokens, first divergence at character 7 for item 3. The gate correctly kept it out of any config. `tests/test_eval_perf.py:73` (`test_real_qwen_greedy_padding_and_static_cache`) passes but compares B1-dynamic with B2-static over 32 tokens and two prompts. That does not cover the production comparison (B32 dynamic vs static at 1024 tokens), so it does not contradict the probe, but the name overstates coverage. Add a guard or doc note stating "not score-equivalent; do not enable".

**N3. Greedy disagreement is not explained; the probe lacks the control that would explain it.** vLLM and static both score 0/32. The useful pattern: in the first 12 probe prompts, HF diverges from both alternates at the same character in 9 cases (items 0, 1, 4–10). In each of those 9, static and vLLM agree with each other beyond that point (static-vs-vLLM first difference lies past the HF divergence). That suggests the HF reference (dynamic cache, left-padded batch of 32) is the outlier rather than either new path. This is a pattern, not a proof. The missing control is HF dynamic at batch 1 (no padding) on the same 32 prompts, plus an HF-vs-HF repeat of the probe. If B1 matches vLLM and static at those points, the padded-batch HF path is the cause, which would affect every canonical score (pre-existing on main, not introduced here). Run this control on GPU before any engine or static change. Not blocking for this branch, because no alternative path is enabled.

**N4. Default `batch_size` 8 → 32 is a silent change for configs that omit the key.** `src/wsp/eval/run.py:217`. Batch composition changes sampled outputs, and `config_hash` does not include the default. All shipped eval configs set `batch_size` (eval_fast/faithful 32, cheap 64), so there is no current effect. Suggest making the key required, or hashing the effective value.

**N5. vLLM worker uses the same seed for every request.** `src/wsp/eval/vllm_worker.py:28`: `seed=cfg["seed"]` on each `SamplingParams`. At T=0.6 every request then draws the same random stream, which is correlated noise across prompts and not HF's batch RNG. Irrelevant for greedy; fix (derive a per-item seed) before any sampled vLLM use. Sampling parameters otherwise match HF (temperature, top_p, top_k, presence_penalty, max_tokens); record schema is identical (keys and prompt strings match 450/450).

**N6. Merge consequence: every canonical signature changes.** `batch.py:189` (`signature = sha256(config_hash + source_hash)`) and `batch.py:30` (`source_hash` covers all `src/wsp/**/*.py`). Merging any `src` change therefore marks all existing `eval.json` entries as stale: `complete()` and `select_entries` will re-evaluate all 1205 production entries on the next resume (about 124 h at 6.15 min/entry). The branch is also 32 commits behind main. Decide, before merge, whether to accept the re-evaluation or scope the hash. The `backend` term added at `batch.py:207` changes nothing further for this purpose.

**N7. Batched choice scoring is unvalidated on real weights.** `run.py:261-294`. Default `choice_batch_size=1` keeps the production path scalar; no shipped config sets it, and N1 shows the scalar path with the new all-ones mask is unchanged. The batched path is covered only by a synthetic model (`tests/test_eval_perf.py:89`). It also passes no `position_ids`, so left-padded rows get shifted positions, and Qwen3.5's gated-delta layers see pad tokens. Validate on real weights before enabling it.

**N8. Compile: disabled by non-selection, reason absent from code and docs.** `PROBE_FAILED=compile` appears only in `/home/ubuntu/agent-logs/perf-benchmark-20261104-075600.log`. The reason is in `data/runs/perf/probe-compile.log`: `torch.compile(mode="reduce-overhead")` fails with "accessing tensor output of CUDAGraphs that has been overwritten" in causal_conv1d `update_conv_state`. `run.py:171-174` compiles whenever `generation["compile"]` is truthy, with no guard. No shipped config or `hf-best.yaml` sets it, so it is not used; if forced, it fails at first forward (loud, not silent). Add a `NotImplementedError` with the reason, and record the failure in `BENCH_EVAL.md`.

**N9. "No engine advantage" and "decode-step bound" are narrower than the doc implies.** HF generation is about 75% of entry wall time (278.9 of 370 s). vLLM ran with `enforce_eager=True`, 0.55 GPU memory, prefix cache off, and two engine restarts per entry. Its probe decode throughput was 16% higher than HF (1415.8 vs 1216.7 tok/s). The conclusion holds for this harness configuration only. The "floor ~6.1 min (decode-step bound)" in `docs/DECISIONS.md` D3 addendum 2 was not measured; soften it.

**N10. Timing definitions need reconciling with D3 planning.** `docs/DECISIONS.md` D3 addendum reports a clean 12.4 min/entry; this doc reports 6.1. The post-zoo run of the same entry (main 49c8321) recorded `minutes` 6.094 but `D2_SECONDS=745` (about 12.4 min process wall). State which definition each figure uses. The D3 subset resolves to exactly 300 entries with the current manifest, which is consistent with the table; the D3 log at `/home/ubuntu/agent-logs/p2-d3-batch-20261104-084933.log` was empty at check time, so D3 wall time is unverified.

**N11. Traceability.** The perf artefacts cited in `BENCH_EVAL.md` live under `data/` (gitignored; the worktree links to the main repo's `data/`). None of it is committed, which is correct (zero tracked `data/` files on the branch; no key patterns in the diff). Reproduction needs that directory; say so.

## Checks, answers to the five questions

1. **HF changes (batch 32, static option, greedy, compile probe).** At production settings, no per-item change: N1 (458/458 identical against main's canonical run). Padding side (`run.py:160`, left), stop logic (`run.py:240-251`), and seed handling (`run.py:215`, one `seed_all` per `generate` call) are unchanged. Static cache changes outputs (N2). Greedy is reached only at temperature 0 (probe and tests), so production T=0.6 is untouched. Batched choice scoring is off by default (N7).
2. **vLLM adapter.** Sampling parameters match except per-request seed (N5). Record schema identical. Temperature-0 agreement is 0/32 and unexplained (N3). Score changes on full entries are unreported (B4). `.venv-vllm` is created in the worktree (install log: "Creating virtual environment at: .venv-vllm"); `.venv` has no vLLM distributions. The probe never reached an early stop (32/32 hit the 1024 budget), so the stop-token convention is untested by the gate; token-count differences vs HF look like sampling divergence (refusal differences up to 193 tokens), with no systematic ±1 offset.
3. **BENCH_EVAL.md numbers.** Traceable: `minutes` in `eval.json` gives 6.177 / 6.152 / 6.104 (hf-b32 / hf-best / vllm). Tokens/s recomputes to 728.3 / 732.5 / 713.9. Denominators: 1205 production entries (manifest has 1243 rows), D3 = 300. Host load not recorded (B3). vLLM tokens/s definition wrong (B4). `hf-best` label wrong (B2).
4. **`PROBE_FAILED=compile`.** Compile is not used, and the reason exists in logs but not in code or docs. Not "correctly disabled with a reason" until N8 is addressed.
5. **Tests, ruff, data.** CPU tests are real assertions (presence penalty with padding, batch padding/crop/EOS with a fake model, choice padding on a synthetic model). The only real-weight test is the opt-in GPU test; `gpu-test.log` shows 1 passed. Ruff check passes; format fails (B1). No data or secrets in the branch diff.
